# Immutable storage layout

Synthetic and real roots are injected separately and must be distinct, non-overlapping paths. The synthetic-only API rejects real records and the synthetic CLI exposes no real-root option.

Each session is published as `session_<id>/` with `manifest/`, `protocol/`, `raw/`, `processed/`, `qc/`, `features/`, `models/`, `reports/`, `events/`, `session_record.json` and `SESSION_COMPLETE`. Raw and canonical normalized config snapshots are copied under `protocol/config/`; the verified manifest and sidecar are copied under `manifest/`.

Runs live at `raw/run_<id>/` and contain `run_record.json`, synthetic metadata/arrays when applicable, and `RUN_COMPLETE`. Files are create-only: bytes first go to a same-directory temporary file, are flushed, then are published without replacing an existing target. Session and run directories are built under same-filesystem staging names and renamed only after required files and completion marker exist. Any pre-publication failure removes staging, so no completed-looking target remains.

Synthetic ESS processing lives at `processed/run_<source_run_id>/processing_<processing_id>/`. The store derives this path from its injected synthetic root and validated session/source run; callers cannot provide a filesystem target or choose the real root. A processing directory contains only `processing_arrays.npz` and sidecar, `processing_receipt.json` and sidecar, `processing_metadata.json`, `processing_record.json`, and `PROCESSING_COMPLETE`. Publication uses a same-filesystem staging directory plus a cooperative create-only lock; a competing or existing target is never replaced, and only the caller-owned staging/lock is cleaned on failure.

After processing directory publication, `processing_created` is appended through the same root-confined event API. It binds the canonical processing record bytes, receipt digest, processing/source/session identities and creation time. The processing directory remains the same seven-file envelope. Event append failure leaves that immutable envelope in place and is reported as `published=true`, so callers must not treat the combined operation as successful. Processing validation requires exactly one strict canonical event for the composite identity `(source_run_id, processing_id)`. Events for a different source run may reuse the same processing ID; a duplicate of the same composite identity is rejected.

Synthetic provisional QC lives at `qc/run_<source_run_id>/processing_<processing_id>/qc_<qc_id>/`. The narrow store API derives this path from its injected synthetic root and requires a completed source run and processing; callers cannot provide a target path or select the real root. A QC directory contains only `qc_metrics.json` and sidecar, `qc_receipt.json` and sidecar, `qc_metadata.json`, `qc_record.json`, and `QC_COMPLETE`. Publication uses same-filesystem staging and a create-only cooperative lock. The post-publication `qc_created` event binds the composite identity `(source_run_id, processing_id, qc_id)`, record/metrics/receipt hashes and creation time. Event failure leaves the seven-file envelope and reports `published=true`; validation requires exactly one matching strict canonical event and never repairs failed bytes.

Synthetic repeatability sets are session-level QC derivatives at `qc/repeat_sets/reassembly_<reassembly_id>/repeat_set_<repeat_set_id>/`. The reassembly is derived from replay-validated member captures, while the caller supplies only the repeat-set ID and member identity triples. The directory contains only `repeatability_metrics.json` and sidecar, `repeatability_receipt.json` and sidecar, `repeatability_metadata.json`, `repeatability_record.json`, and `REPEATABILITY_COMPLETE`. Publication uses the same synthetic confinement, staging, create-only lock and failure cleanup. Before any repeatability directory, parent, staging path or lock can be created, the AnalysisConfig provenance and five null baseline/decision fields are audited. The `1.1.0` receipt, record and metadata carry one shared strict not-evaluated/no-baseline/no-threshold/no-drift state. The `repeatability_created` event remains `1.0.0` and binds composite identity `(reassembly_id, repeat_set_id)`, new record/receipt hashes, metrics hash, normalized member-list hash and time. Validation requires exactly one matching canonical event and is read-only.

Existing session IDs, run IDs, artifacts and numbered event files fail rather than overwrite. Events use monotonically numbered create-only JSON files. Artifact validation confines the relative path to the selected session and recomputes byte size and SHA256. Session validation also validates every completed run and referenced artifact.

The public event API is `append_event(origin, session_id, event, payload)`. It never accepts a caller-selected session filesystem path: the store derives the resolved session from its injected DataRoots, verifies root containment, `SESSION_COMPLETE`, SessionRecord identity/origin and the resolved events directory before writing. Event names are restricted to ASCII letters, digits, hyphens and underscores. Payloads cannot replace the system-owned `event`, `sequence`, `session_id` or `data_origin` fields. A numbering race fails through the same create-only atomic publication and cannot replace the competing event.

The immutable session record is not rewritten when a run is appended; the append-only event ledger and immutable run records capture that evolution. Callers that know a planned run set may place it in the initial SessionRecord.

The processing, QC and repeatability event ledger is an internal integrity/audit relationship, not a signed or externally witnessed security log. It does not claim protection against coordinated malicious rewriting of both event and artifact bytes or every TOCTOU actor.

DEV-04.04 condition-aware captures retain the existing raw-run envelope and root confinement, but use a versioned receipt that binds the development condition plan, Stage 1 protocol, complete resolved node-state map, manifest-derived delays/weights and synthetic response digest. They remain synthetic-only and set every hardware, playback, recording, calibration, formal and experimental flag false.

Baseline differences live at `processed/baseline_differences/comparison_<comparison_id>/`. The store derives this target only from the injected synthetic root, validated session and safe comparison ID. The exact 11 files are condition binding plus sidecar, deterministic arrays NPZ plus sidecar, canonical metrics plus sidecar, canonical receipt plus sidecar, metadata, record and `BASELINE_DIFFERENCE_COMPLETE == b"complete\n"`. Publication uses a create-only lock, same-filesystem staging and atomic directory rename; failed staging is removed, an existing target is never replaced, and post-publication event failure reports `published=true` without deleting the completed envelope.

One canonical `baseline_difference_created` event binds the comparison identity, both derived reassembly/repeat-set identities, both normalized member lists, condition binding, arrays, metrics, receipt, record and aware creation time. Validation first revalidates both complete condition-aware repeatability chains, then deterministically rebuilds every payload and requires the exact file set, canonical JSON, exact sidecars and completion bytes. It is read-only and does not repair failures. This is project-internal integrity/audit linkage, not a signature, witness or trusted timestamp.

DEV-05.01 protocol plans use a separate, single-purpose development root rather than either session data root. A plan is published at `plans/plan_<plan_id>/` with exactly compiled plan plus sidecar, receipt plus sidecar, metadata, outer record and `PROTOCOL_PLAN_COMPLETE == b"complete\n"`. The store has no real/synthetic selector and no arbitrary output-path parameter. Compilation and the measurement-count limit run before the root is created; publication then uses a same-filesystem staging directory, create-only lock and no-replace rename.

Plan validation is read-only: it rereads manifest/sidecar, all bundle configs, formal draft protocol and development spec, recompiles the full matrix and schedule, and compares canonical bytes. Plans are not sessions and therefore deliberately create no session, run, event, raw, processed, QC, feature or model directories.
