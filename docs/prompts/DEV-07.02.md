## 二、本步骤目标

实现 Windows 本地最小 Tkinter 实验向导，使操作者能够清楚看到：

- 当前实验阶段
- 当前 Session
- 当前 Reassembly
- 当前条件
- N1–N6 的具体装配要求
- 当前需要操作者完成什么
- 当前由程序执行什么
- 两次重复测量的进度
- 整体实验进度

本步骤完成后，应能通过 fake backend 演练完整的“装配确认 → 两次测量 → 下一条件”流程，但不得产生任何真实声音或真实录音。

## 三、角色必须清晰区分

界面必须明显区分：

### `[用户操作]`

用户负责：

- 根据界面装配当前条件
- 检查 N1–N6
- 确认耳机未佩戴
- 确认装置状态
- 点击开始当前条件
- 必要时暂停或紧急停止

### `[程序执行]`

程序负责：

- 读取计划
- 显示当前条件
- 调用 fake backend
- 自动执行连续两次重复测量
- 保存 demo 结果
- 更新进度
- 两次完成后进入下一条件的装配等待状态

界面中不要使用含糊的单一状态文字。当前是用户操作还是程序操作必须一眼可见。

## 四、实现原则

### 4.1 使用 Tkinter

- 使用 Python 标准库 `tkinter`。
- 不增加 Qt、Electron、Web 前端或其他 GUI 框架。
- 不增加数据库。
- 不增加安装器。
- 不制作复杂主题系统。
- 界面文字以中文为主。
- 优先保证清晰、稳定和易操作。

### 4.2 适配现有架构

先检查现有项目结构，再决定文件位置。

必须复用：

- 现有 Stage 1–4 计划和条件模型
- 现有 plan/compiler 或 manifest 读取逻辑
- DEV-07.01 的 fake backend 和 capture core
- 现有 create-only 采集包持久化
- 现有异常和类型体系

不得：

- 在 UI 内重新实现 ESS
- 在 UI 内重新实现采集
- 复制一套 Stage 1–4 条件定义
- 将业务逻辑全部写进 Tkinter callback
- 重构整个项目

将“实验流程控制器”和“Tkinter 界面”适度分离，使主要流程能够在不打开窗口的情况下测试。

不要建立复杂的 MVVM、插件系统、事件总线或依赖注入框架。

## 五、最小界面

主窗口至少包含以下区域。

### 5.1 顶部状态区

显示：

- 项目：Acoustic Ladder V1.3
- 当前模式：`模拟演练 / FAKE BACKEND`
- 明显警告：`当前未连接真实硬件，不会播放或录音`
- Stage
- Session
- Reassembly
- 当前条件序号 / 当前阶段条件总数
- 当前测量重复：`0/2`、`1/2` 或 `2/2`
- 总体进度

模拟模式标识必须持续可见，不能只在启动时显示一次。

### 5.2 当前装配区

用六个清晰方框或标签显示：

- N1
- N2
- N3
- N4
- N5
- N6

每个节点显示当前需要安装：

- `BLK`
- `B28`
- `B32`
- `B40`

必须从现有条件计划读取，不得由 UI 自行推导另一套配置。

显示简短说明，例如：

- `BLK：封闭件`
- `B28：2.8 mm 桥件`
- `B32：3.2 mm 桥件`
- `B40：4.0 mm 桥件`

如果现有正式命名不同，以仓库中的 canonical 命名为准。

### 5.3 用户操作确认区

每次进入新条件时，以下确认框必须重置：

- `我已按 N1–N6 提示完成装配`
- `我已确认耳机没有佩戴在耳朵上`
- `我已确认装置及输入/输出端位置正确`

三个确认全部选中前，“开始当前条件测量”按钮必须禁用。

即使当前为模拟模式，也保留这些确认，用于演练正式流程。

### 5.4 程序执行区

显示：

- 当前程序状态
- 当前正在执行第几次重复
- 最近一次 fake capture 的结果
- 简短错误信息
- 下一步提示

状态至少区分：

- 等待用户装配
- 准备开始
- 正在执行重复 1/2
- 正在执行重复 2/2
- 当前条件完成
- 已暂停
- 已取消
- 出错
- 全部完成

不要增加实时频谱、波形动画或复杂日志浏览器。

### 5.5 操作按钮

至少提供：

- `开始当前条件测量`
- `暂停`
- `继续`
- `紧急停止`
- `退出`

行为要求：

- 点击开始后自动依次执行两次 fake capture。
- 两次之间不需要用户再次点击。
- 两次都成功后，自动切换到下一条件。
- 切换到下一条件后，必须回到“等待用户装配”。
- 不得跳过下一条件的用户确认。
- 运行期间禁止重复点击开始。
- 暂停只允许发生在两次测量之间或条件之间。
- 正在执行单次 capture 时，暂停不得伪装成中断；需要立即终止时使用“紧急停止”。
- 紧急停止必须调用 DEV-07.01 的取消机制。
- 取消的 capture 不得标记为成功。
- 出错后不得自动开始下一条件。

## 六、实验计划显示

- Stage 1：19 个条件，152 次 sweep
- Stage 2：4 个条件，32 次 sweep
- Stage 3：4 个条件，32 次 sweep

这些数字必须来自现有计划或经过现有计划数据验证，不能在多处复制成互不关联的常量。

### 6.2 本步骤只运行小型 demo

为开发和验收提供一个明确标记的 demo plan，例如：

- 2–3 个条件
- 每个条件2次重复

demo plan 必须：

- 与正式实验数据目录隔离
- 明确标记为 `development_demo`
- 不能被误认为正式实验
- 不创建正式实验结论

正式计划本步骤只用于浏览和流程兼容性验证。

## 七、状态与恢复

使用简单的 `session_state.json` 保存可恢复状态。

至少保存：

- schema/version 字段，但不新增独立 JSON Schema 文件
- session ID
- 模式：`development_demo`
- 当前 Stage
- 当前条件索引
- 当前 repeat
- 已完成条件
- 当前控制器状态
- demo 数据根目录
- 最后更新时间

要求：

- 使用临时文件加原子替换更新状态。
- `session_state.json` 是可变的运行状态，不是不可变实验凭证。
- 正式 capture bundle 仍使用 DEV-07.01 的 create-only 机制。
- 退出后重新打开 UI，可以选择继续未完成的 demo session。
- 已完成的 repeat 不得重复标记。
- 状态文件损坏、字段缺失或与计划不一致时：
  - 不得猜测恢复
  - 显示明确错误
  - 不覆盖原状态
- 不实现复杂迁移系统。

关闭窗口时：

- 如果没有 capture 正在运行，先保存状态再退出。
- 如果 capture 正在运行，必须先请求取消并等待安全结束，再退出。
- 不得留下“仍在运行”的虚假状态。

## 十、线程与 Tkinter 安全

Tkinter 控件只能从主线程更新。

fake capture 可以在后台线程执行，但必须：

- 通过简单队列或 `after()` 将结果传回主线程
- 防止重复启动
- 正确处理窗口关闭
- 正确传递取消请求
- 不让后台异常导致 UI 永久卡在“运行中”

不要引入异步框架或复杂线程池。

## 十一、测试要求（精简版）
