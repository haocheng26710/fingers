# Data roots

Do not commit generated sessions here. Runtime synthetic and real data must use separate, non-overlapping roots supplied by the operator. The synthetic CLI accepts only `--synthetic-root` and cannot select a real root.

For reproducible interface testing, use a fresh directory under the operating-system temporary directory as shown in the repository README. A session/run ID is immutable once published; validation recomputes artifact hashes and rejects incomplete or tampered data.

DEV-03.03 offline ESS fixtures follow the same separation rule but are not sessions or real data. Supply a dedicated temporary `development-root`; each artifact ID is create-only and its WAV/metadata bundle is regenerated during validation. Never point the development fixture command at a real-data root. Offline fixtures are not measurements, formal inputs, or authorized playback material.

DEV-03.04 virtual captures may be published only through the synthetic-only API/CLI into an existing completed synthetic session. The caller supplies identifiers, a validated full configuration bundle, one validated offline ESS artifact, and one strict project-relative scenario; it cannot select `DataOrigin.REAL` or provide waveform/hash/receipt facts. The scenario source is re-read at publication and validation, so its current raw bytes, parsed model, normalized bytes, hashes, and project-relative identity must still match the loaded object. Successful runs are create-only and contain immutable output-reference and simulated-input WAVs plus provenance. The receipt and run share one non-negative measurement order; canonical synthetic metadata, the complete run envelope, and the stored manifest sidecar are validator-enforced contracts. Failed or aborted schedules publish no completed run and clean only their own staging. Validation is read-only and deterministically replays the software schedule. These artifacts are not recordings, measurements, hardware-duplex evidence, or experimental results.

DEV-04.01 processing may target only a completed virtual capture inside the injected synthetic root. The public API accepts source/session/processing identifiers and the same validated bundle, scenario, and ESS source; it accepts no arbitrary path under `processed/`, no real root, waveform, expected latency/gain, precomputed output, or device parameter. Results are create-only under `processed/run_<source_run_id>/processing_<processing_id>/`, and the validator revalidates the source capture and recomputes every array. Processing output is a deterministic development fixture, not a measurement or experimental result.

DEV-04.02 provisional QC may target only a completed, replay-valid processing artifact inside the injected synthetic root. Its public API accepts session/source-run/processing/QC identifiers and the original validated provenance inputs; it accepts no arbitrary QC target, real root, waveform, array, precomputed metric, scenario truth, threshold, decision or device parameter. Results are create-only under `qc/run_<source_run_id>/processing_<processing_id>/qc_<qc_id>/`; validation revalidates processing and recomputes the metrics. These metrics are threshold-free development evidence, not hardware readiness, formal QC, a pass/fail decision, a calibrated result or an experimental result.

DEV-04.03R repeatability may combine only replay-valid synthetic capture/processing/QC identities from one session and one reassembly with distinct consecutive measurement orders. Reassembly, order, all waveform/array facts and all provenance are derived from stored evidence. Results are create-only under `qc/repeat_sets/reassembly_<reassembly_id>/repeat_set_<repeat_set_id>/`; the real root is never selected. The receipt/algorithm/record `1.1.0` envelope records explicit not-evaluated, baseline-not-assigned/deferred, drift-not-evaluated and threshold false/null states. A non-null baseline-selection rule or QC/effect/drift/classification threshold is rejected before any repeatability write. Old `1.0.0` repeatability artifacts must be regenerated. The current contract still has no protocol-condition binding, BLK baseline assignment, baseline difference, threshold/pass-fail application, drift decision, hardware/calibration/SPL claim or experimental result.

DEV-06.01 analyses are independent derivatives under a dedicated synthetic storage root at `analyses/analysis_<analysis_id>/`; they are never written into a completed execution or session envelope. The store derives the target from a safe ID and its injected root. Each exact 15-file envelope binds four replay-valid Stage 1–4 execution completions, all 344 source runs, row/QC metadata, same-group all-BLK references, a 16-column feature schema, grouped split plan and deterministic full-array NPZ. Validation recomputes every row and writes nothing. These files are provisional development matrices, not real data, experimental measurements, model output or hardware evidence.
